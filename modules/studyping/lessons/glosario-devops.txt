## 1. CONTAINER ORCHESTRATION & PLATFORM INFRASTRUCTURE

### 1.1 Kubernetes Vanilla vs. Red Hat OpenShift Enterprise

*   **Kubernetes (Vanilla):** Sistema open-source de orquestación de contenedores que automatiza el despliegue, escalado y administración de aplicaciones en contenedores. Se compone del **Control Plane** (`kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`) y de los **Worker Nodes** (`kubelet`, `kube-proxy`, Container Runtime como `containerd` o `CRI-O`).
*   **Red Hat OpenShift Enterprise:** Plataforma de aplicación de contenedores empresarial construida sobre Kubernetes Vanilla (usando `CRI-O` y Red Hat Enterprise Linux CoreOS - RHCOS). Agrega una capa de gobernanza, seguridad estricta out-of-the-box, experiencia de desarrollador integrada y automatización de ciclo de vida del clúster mediante **Operators** (Operator Lifecycle Manager - OLM).

#### Comparativa Arquitectónica Directa

| Dimensión de Plataforma | Kubernetes Vanilla | Red Hat OpenShift Enterprise |
| :--- | :--- | :--- |
| **Control de Acceso / Seguridad** | RBAC (`Role`, `ClusterRole`, `RoleBinding`) | RBAC + **Security Context Constraints (SCC)** (`restricted-v2`, `anyuid`, `privileged`) |
| **Enrutamiento HTTP/HTTPS** | `Ingress` Controller (NGINX, Traefik, HAProxy) | **`Route`** (HAProxy Router nativo con terminación SSL Edge, Passthrough, Re-encrypt) |
| **Aislamiento de Recursos** | `Namespace` | **`Project`** (Namespace enriquecido con anotaciones, cuotas por defecto y plantillas) |
| **Gestión de Componentes** | Helm Charts, Kustomize, Manifestos YAML directos | **Operators (OLM)**, BuildConfigs, ImageStreams, Helm, Kustomize |
| **CLI Principal** | `kubectl` | `oc` (superconjunto de `kubectl` con comandos orientados a proyectos y seguridad) |

> *"While Kubernetes Vanilla provides the fundamental primitives for container orchestration, Red Hat OpenShift elevates this to an enterprise platform by embedding strict security defaults such as Security Context Constraints (SCCs), native ingress abstractions via Routes, and automated cluster lifecycle management through the Operator Lifecycle Manager (OLM). In my experience at Globant and PayU, while Vanilla Kubernetes requires assembling third-party tools for ingress, RBAC enforcement, and build pipelines, OpenShift provides an integrated developer experience with out-of-the-box compliance suitable for financial and enterprise workloads."*

#### Practical Scripting Example: Bash Audit Script for Pod Security Compliance
Este script en Bash audita qué contenedores en un proyecto de OpenShift o clúster de Kubernetes están configurados con permisos de ejecución o contextos de usuario no especificados.

```bash
#!/usr/bin/env bash
# audit_pod_security.sh - Audita Pods y contextos de seguridad en el namespace.
set -euo pipefail

NAMESPACE="${1:-default}"
echo "[+] Auditing Security Context for Pods in namespace/project: '${NAMESPACE}'"

# Extrae informacion de seguridad de pods usando kubectl y jq
kubectl get pods -n "${NAMESPACE}" -o json | jq -r '
  .items[] | 
  .metadata.name as $pod | 
  .spec.containers[] | 
  {
    pod: $pod,
    container: .name,
    runAsUser: (.securityContext.runAsUser // "NotSpecified"),
    privileged: (.securityContext.privileged // false)
  } | 
  select(.runAsUser == "NotSpecified" or .privileged == true) |
  "Audit Alert -> Pod: \(.pod) | Container: \(.container) | RunAsUser: \(.runAsUser) | Privileged: \(.privileged)"
'

echo "[+] Audit completed."
```

### 1.2 Kubernetes Workload Lifecycles & Health Probes

*   **Liveness Probe:** Determina si el contenedor necesita ser reiniciado. Si falla la sonda, el `kubelet` destruye el contenedor y aplica la política de reinicio (`RestartPolicy`).
*   **Readiness Probe:** Determina si el contenedor está listo para recibir tráfico de red. Si falla, el controlador de `Endpoints` remueve la IP del Pod del Service de Kubernetes, evitando errores 502/503.
*   **Startup Probe:** Deshabilita temporalmente las sondas de Liveness y Readiness durante el arranque de aplicaciones pesadas. Evita reinicios prematuros durante la inicialización.

#### Diagnóstico Forense de Estados de Pods

*   **`CrashLoopBackOff`:** El contenedor inicia, falla (exit code != 0), se reinicia y vuelve a fallar repetidamente. El tiempo entre reinicios se incrementa exponencialmente (10s, 20s, 40s... hasta 5m).
    *   *Causas comunes:* Excepciones no capturadas en la aplicación, variables de entorno faltantes, falla de conexión a base de datos al arrancar, memoria insuficiente.
*   **`ImagePullBackOff` / `ErrImagePull`:** El `kubelet` no puede descargar la imagen del contenedor especificada.
    *   *Causas comunes:* Tag de imagen inexistente, nombre del registry mal escrito, credenciales expiradas o faltantes en el `imagePullSecret`, políticas de red bloqueando salida al registry Quay.
*   **`OOMKilled` (Exit Code 137):** El Kernel de Linux invocó el OOM Killer y detuvo el contenedor por sobrepasar el límite de memoria (`limits.memory`).

#### Practical Scripting Example: Python Script for Automated Workload Diagnostics
Este script de Python interactúa con la API de Kubernetes para analizar el estado de Pods no saludables en el clúster y extraer la causa del fallo.

```python
#!/usr/bin/env python3
"""
k8s_workload_diagnoser.py
Diagnostica cargas de trabajo en Kubernetes identificando el Exit Code exacto, 
razon de fallo y logs del contenedor previo a la caida.
"""
import sys
from kubernetes import client, config
from kubernetes.client.rest import ApiException

def diagnose_unhealthy_pods(namespace="default"):
    try:
        config.load_kube_config()
    except Exception:
        config.load_incluster_config()

    v1 = client.CoreV1Api()
    print(f"[*] Scanning pods in namespace: '{namespace}'...")

    try:
        pods = v1.list_namespaced_pod(namespace)
        for pod in pods.items:
            pod_name = pod.metadata.name
            status = pod.status
            
            if status.container_statuses:
                for cs in status.container_statuses:
                    last_state = cs.last_state
                    
                    if cs.restart_count > 3:
                        print(f"\n[!] HIGH RESTART COUNT detected on Pod: {pod_name} (Restarts: {cs.restart_count})")
                        
                        if last_state.terminated:
                            exit_code = last_state.terminated.exit_code
                            reason = last_state.terminated.reason
                            print(f"    -> Last Termination Reason: {reason} (Exit Code: {exit_code})")
                            if exit_code == 137:
                                print("    -> DIAGNOSIS: OOMKilled (Out of Memory). Increase container memory limit.")
                            elif exit_code == 1:
                                print("    -> DIAGNOSIS: Application runtime crash. Check application logs.")
                        
                        try:
                            logs = v1.read_namespaced_pod_log(
                                name=pod_name, 
                                namespace=namespace, 
                                container=cs.name, 
                                previous=True, 
                                tail_lines=10
                            )
                            print(f"    --- Last Logs (Previous Container) ---\n{logs.strip()}")
                        except ApiException as e:
                            print(f"    -> Could not fetch previous logs: {e.reason}")

    except ApiException as e:
        print(f"Error connecting to Kubernetes API: {e}", file=sys.stderr)

if __name__ == "__main__":
    ns = sys.argv[1] if len(sys.argv) > 1 else "default"
    diagnose_unhealthy_pods(ns)
```

## 2. GITOPS, RECONCILIATION & CONTINUOUS DELIVERY (ARGO CD)

### 2.1 Principios de GitOps & Arquitectura de Argo CD

*   **GitOps:** Modelo operacional donde el repositorio de Git es la **única fuente de verdad** (*Single Source of Truth*) para el estado deseado de la infraestructura y aplicaciones. Cualquier cambio se realiza mediante Pull Requests (PRs).
*   **Argo CD:** Controlador de entrega continua declarativo y nativo de Kubernetes que implementa GitOps. Monitorea el repositorio Git (estado deseado) y lo compara continuamente contra el clúster activo (estado actual).
*   **Reconciliación (Reconciliation Loop):** Proceso automatizado en el que Argo CD detecta la discrepancia (*Drift*) entre el estado deseado en Git y el estado real en Kubernetes, y aplica las modificaciones necesarias para igualar el clúster a Git.

#### Troubleshooting de Estados en Argo CD

*   **Estado `OutOfSync`:** El manifiesto desplegado en el clúster difiere del manifiesto guardado en Git.
    *   *Causas:* Cambios manuales directos en el clúster (`kubectl edit`), diferencias en anotaciones agregadas por mutadores/admission webhooks, o commits recientes en Git no sincronizados.
*   **Estado `Degraded`:** La aplicación está sincronizada (`Synced`), pero uno o más recursos de Kubernetes no alcanzaron el estado saludable (`Healthy`).
    *   *Causas:* Pods en `CrashLoopBackOff`, Deployments con `ProgressDeadlineExceeded`, PVCs que no pueden montarse, o Services apuntando a Selectors inexistentes.

#### Practical Scripting Example: Bash Script para Deployment & Automated Rollback con Argo CD CLI
Este script automatiza la sincronización de una aplicación en Argo CD y ejecuta un rollback si no alcanza el estado saludable dentro del timeout.

```bash
#!/usr/bin/env bash
# sync_and_rollback_argocd.sh - Sincroniza Argo CD con verificacion de salud y rollback.
set -euo pipefail

ARGOCD_APP="${1:?Application name required}"
TIMEOUT_SECONDS=300

echo "[*] Triggering Argo CD Sync for Application: '${ARGOCD_APP}'..."

# Dispara la sincronizacion de Argo CD usando la CLI
argocd app sync "${ARGOCD_APP}"

echo "[*] Waiting for application to reach Healthy and Synced status..."

if argocd app wait "${ARGOCD_APP}" --health --synced --timeout "${TIMEOUT_SECONDS}"; then
    echo "[SUCCESS] Application '${ARGOCD_APP}' successfully deployed and healthy."
else
    echo "[ERROR] Deployment failed or timed out. Initiating Rollback!"
    
    # Obtiene la revision previa y realiza rollback
    PREVIOUS_REVISION=$(argocd app history "${ARGOCD_APP}" | awk 'NR>1 {print $1}' | tail -n 2 | head -n 1)
    
    echo "[*] Rolling back '${ARGOCD_APP}' to Revision ID: ${PREVIOUS_REVISION}..."
    argocd app rollback "${ARGOCD_APP}" "${PREVIOUS_REVISION}"
    
    echo "[!] Rollback completed. Check application logs."
    exit 1
fi
```

## 3. CI/CD PIPELINES, AUTOMATION & GOVERNANCE (AZURE DEVOPS)

### 3.1 Azure DevOps Pipelines (Multi-Stage YAML)

*   **Stages:** Divisiones lógicas principales en el pipeline (ej. `Build`, `SecurityScan`, `DeployToStaging`, `DeployToProduction`).
*   **Jobs:** Colección de pasos ejecutados de manera secuencial dentro del mismo **Agent** (máquina virtual o runner).
*   **Steps / Tasks:** Instrucciones individuales como ejecución de comandos Bash, compilación de código o invocación de herramientas.
*   **Service Connections:** Credenciales seguras (usando Service Principals de Azure o Workload Identity Federation) que permiten al pipeline conectarse a recursos externos como clústeres de Kubernetes/OpenShift o registrios Quay.

### 3.2 Gobernanza, Secretos y Quality Gates

*   **Variable Groups & Azure Key Vault:** Gestión centralizada de secretos. Inyecta variables de entorno de manera efímera y encriptada en tiempo de ejecución.
*   **Quality Gates & Approvals:** Reglas estrictas en Azure DevOps Environments donde un despliegue a producción requiere aprobación manual o verificación automatizada de seguridad.

#### Practical Scripting Example: Production Multi-Stage Azure DevOps Pipeline (`azure-pipelines.yml`)
Pipeline declarativo multi-etapa para compilación, escaneo de contenedor y actualización de manifestos GitOps.

```yaml

  branches:
    include:
      - main

variables:
  - group: Production-Secrets
  - name: imageRepository
    value: 'sffcu/digital-banking-api'
  - name: containerRegistry
```

## 4. DEVSECOPS, CONTAINER REGISTRIES & CODE QUALITY

### 4.1 Red Hat Quay & Gobernanza de Imágenes

*   **Red Hat Quay:** Registrio empresarial de imágenes de contenedor que ofrece alta disponibilidad, almacenamiento de artefactos OCI, escaneo de seguridad (Clair), RBAC, Robot Accounts para CI/CD e inmutabilidad de tags.
*   **Robot Accounts:** Credenciales de servicio específicas para automatización CI/CD con permisos mínimos restringidos.
*   **Image Retention Policies:** Reglas de expiración que purgan automáticamente tags antiguas, evitando el agotamiento de almacenamiento.
*   **`imagePullSecrets`:** Recurso de Kubernetes tipo `kubernetes.io/dockerconfigjson` que contiene las credenciales encriptadas para autenticación contra Red Hat Quay.

### 4.2 Veracode & Code Quality Security Gates

*   **Veracode:** Plataforma de seguridad de código que proporciona:
    *   **SAST (Static Application Security Testing):** Análisis estático del código fuente para detectar vulnerabilidades OWASP Top 10.
    *   **DAST (Dynamic Application Security Testing):** Análisis dinámico probando la aplicación en ejecución.
    *   **SCA (Software Composition Analysis):** Escaneo de dependencias y bibliotecas open-source para identificar CVEs.

#### Practical Scripting Example: Python Script for Parsing Vulnerability Scans & CI Gate Enforcement
Este script procesa el reporte JSON de escaneo de seguridad y detiene el pipeline si existen vulnerabilidades críticas.

```python
#!/usr/bin/env python3
"""
parse_security_gate.py
Procesa un JSON de escaneo de vulnerabilidades y aplica la barrera de calidad.
"""
import json
import sys

CVSS_CRITICAL_THRESHOLD = 9.0

def evaluate_vulnerabilities(json_file):
    print(f"[*] Analyzing security scan report: {json_file}")
    try:
        with open(json_file, 'r') as f:
            data = json.load(f)
    except FileNotFoundError:
        print(f"[ERROR] Scan file {json_file} not found!", file=sys.stderr)
        sys.exit(2)

    critical_count = 0
    failed_cves = []

    results = data.get("Results", [])
    for result in results:
        vulnerabilities = result.get("Vulnerabilities", [])
        for vuln in vulnerabilities:
            severity = vuln.get("Severity", "UNKNOWN")
            cve_id = vuln.get("VulnerabilityID", "N/A")
            pkg_name = vuln.get("PkgName", "N/A")
            score = vuln.get("CVSS", {}).get("nvd", {}).get("V3Score", 0.0)

            if severity == "CRITICAL" or score >= CVSS_CRITICAL_THRESHOLD:
                critical_count += 1
                failed_cves.append(f"{cve_id} in {pkg_name} (CVSS: {score})")

    if critical_count > 0:
        print(f"\n[FAIL] QUALITY GATE FAILED! Found {critical_count} CRITICAL vulnerabilities:")
        for cve in failed_cves:
            print(f"  - {cve}")
        sys.exit(1)
    else:
        print("[SUCCESS] Quality Gate Passed. No critical vulnerabilities found.")
        sys.exit(0)

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python parse_security_gate.py <scan_results.json>")
        sys.exit(1)
    evaluate_vulnerabilities(sys.argv[1])
```

## 5. OBSERVABILITY, SRE METRICS & PRODUCTION TROUBLESHOOTING

### 5.1 Las 4 Señales Doradas de SRE (Google SRE Book)

1.  **Latencia (Latency):** Tiempo empleado en procesar una solicitud (diferenciando peticiones exitosas vs erróneas).
2.  **Tráfico (Traffic):** Demanda impuesta al sistema (RPS, transacciones por segundo).
3.  **Errores (Errors):** Tasa de peticiones que fallan (HTTP 5xx, excepciones no controladas).
4.  **Saturación (Saturation):** Fracción de recurso de infraestructura utilizado (CPU, RAM, conexión a BD).

### 5.2 PromQL & Consultas de Producción para Grafana

*   **Tasa de Errores HTTP 5xx (5m Rate):**
    ```promql
    sum(rate(http_requests_total{status=~"5.."}[5m])) by (service) 
    / 
    sum(rate(http_requests_total[5m])) by (service) * 100
    ```
*   **Percentil 99 de Latencia (P99 Latency):**
    ```promql
    histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))
    ```
*   **Saturación de Memoria por Pod en Kubernetes:**
    ```promql
    sum(container_memory_working_set_bytes{container!=""}) by (pod) 
    / 
    sum(kube_pod_container_resource_limits{resource="memory"}) by (pod) * 100
    ```

### 5.3 Splunk SPL (Search Processing Language) & Correlación de Logs

*   **Búsqueda de Excepciones y Agrupación por Error:**
    ```spl
    index=digital_banking_prod sourcetype=kubernetes_logs "ERROR" OR "Exception"
    | stats count by service_name, error_code, message
    | sort - count
    ```
*   **Seguimiento de una Transacción Específica mediante Trace ID:**
    ```spl
    index=digital_banking_prod trace_id="txn-948201-bf84"
    | table _time, service_name, log_level, message, duration_ms
    | sort _time asc
    ```

#### Practical Scripting Example: Python Prometheus API Metrics Fetcher
Consulta la API REST de Prometheus para verificar la saturación de memoria antes de autorizar un despliegue.

```python
#!/usr/bin/env python3
"""
check_prometheus_saturation.py
Consulta la API REST de Prometheus para verificar la saturacion de memoria.
"""
import urllib.request
import urllib.parse
import json
import sys

PROMETHEUS_URL = "http://prometheus-k8s.monitoring.svc:9090"
QUERY = 'sum(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / sum(node_memory_MemTotal_bytes) * 100'

def check_cluster_saturation():
    encoded_query = urllib.parse.urlencode({'query': QUERY})
    url = f"{PROMETHEUS_URL}/api/v1/query?{encoded_query}"

    print(f"[*] Querying Prometheus metric: {QUERY}")
    try:
        req = urllib.request.Request(url)
        with urllib.request.urlopen(req, timeout=10) as response:
            data = json.loads(response.read().decode('utf-8'))
            
            if data.get("status") == "success":
                results = data["data"]["result"]
                if results:
                    saturation = float(results[0]["value"][1])
                    print(f"[+] Memory Saturation: {saturation:.2f}%")
                    if saturation > 85.0:
                        print("[WARNING] Saturation > 85%! Deployment aborted.", file=sys.stderr)
                        sys.exit(1)
                    else:
                        print("[SUCCESS] Cluster memory usage is healthy.")
                        sys.exit(0)
    except Exception as e:
        print(f"[ERROR] Failed to query Prometheus API: {e}", file=sys.stderr)
        sys.exit(2)

if __name__ == "__main__":
    check_cluster_saturation()
```

## 6. CORE LINUX ENTERPRISE (RHEL) & PRODUCTION TROUBLESHOOTING

### 6.1 Diagnóstico en Producción RHEL

*   **Almacenamiento e Inodos:** `df -h` (espacio GB), `df -i` (inodos), `du -sh /*` (consumo directorios), `lsof +L1` (archivos borrados retenidos por procesos).
*   **Red y Sockets:** `ss -tuln` (sockets en escucha), `curl -ivk` (handshake TLS/HTTP), `dig +short` (resolución DNS).
*   **Procesos y Recursos:** `top` / `htop` (carga CPU/RAM), `free -h` (memoria libre/cache), `journalctl -u kubelet -f` (logs systemd).

#### Practical Scripting Example: Bash Linux Enterprise Health Checklist
Script para ejecutar auditorías rápidas en servidores RHEL durante la resolución de incidentes.

## 7. QUICK REFERENCE LARPING protsoy FRAMING

1.  **On Kubernetes & OpenShift Operations:**
    > *"In my experience managing production workloads, the key difference between Vanilla Kubernetes and OpenShift lies in enterprise governance. On OpenShift, I heavily utilize Security Context Constraints (SCCs) to prevent pods from running as privileged users, and native Routes for edge TLS termination. When troubleshooting workload crashes, I systematically inspect probe failures, `lastState.terminated.exitCode`, and node resource pressure before altering deployment specs."*

2.  **On Argo CD & GitOps Workflows:**

When managing Argo CD, I set up automated reconciliation with self-healing enabled for non-production environments, while enforcing manual sync gates for production releases.     > *"When designing Azure DevOps multi-stage pipelines from scratch, I separate the build/testing stages from deployment stages using environment approvals and Azure Key Vault integration for zero-trust secret handling. I enforce security quality gates by shifting security left—running container scanners like Trivy or Quay Clair and static analysis tools like Veracode directly in the pipeline, breaking the build if critical CVEs are detected."*

4.  **On Observability & SRE Mindset:**
    > *"I approach system reliability through the lens of Google SRE's 4 Golden Signals: Latency, Traffic, Errors, and Saturation. Using Prometheus and Grafana, I set up alert rules based on SLO burn rates rather than raw metrics. When an incident occurs in digital banking environments, I correlate application logs using Splunk trace IDs with container metrics to isolate whether the root cause is a database connection pool exhaustion or a memory leak in the microservice."*
